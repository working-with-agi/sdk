# 工場見積もり比較 × 不確実性下のエンジン入場計画（SAA ＋ モンテカルロ）

[`engine-mro-optimization`](../engine-mro-optimization/) の第2弾です。
第1弾が「いつ・どのワークスコープで」を確定的に決めるのに対し、本サンプルは
**複数工場の見積もりを比較し、費用超過・TAT 遅延・非計画取卸しの不確実性を
モンテカルロで扱って**、次を同時に決めます。

- 各入場予定エンジンの **工場・ワークスコープ・入場月**
- 期間中に長期リースする **予備エンジン台数**

> データは説明用の合成値です。OEM・実在工場の見積もりではありません。

## 会社ごとの計画（実務に合わせた形、`company.py`）

公開情報で点検した結果（`PRACTICE.md`）に合わせ、問題の立て方を次のように直しました。

- **会社ごとに別の計画**：JAL グループ（JAL・JTA の 737-800 56 機、保有エンジン 123 基）と ANA（39 機、86 基）。
- **工場は契約先 1 つ**：JAL は GE との整備契約（2021 年、5 年）、ANA は MTU Maintenance 珠海（2032 年末まで）。日々の判断は「いつ入場させるか × どこまで直すか」で、工場を選び直すのは契約更新のとき（下の 5 工場の比較は、その入札のユースケース）。
- **契約は実費精算**：分解で見つかった追加作業の費用は全額自社負担。整備費は 2020 年の公開例を 2026 年に外挿（CORE 7.9M$、FULL 11.0M$）。工期は現状の混雑（上側の裾が長い）を反映。
- **根拠のない数字は `no_source`** として `data/companies.json` に明記（予備エンジン数、契約の受け入れ基数、キットの納期、緊急手配の割増など）。感度分析の対象です。

```bash
python company.py jal ana                                            # data/<会社>/fleet.json・shops.json を作る
python baseline.py freeze  --company jal --out baselines/jal-2026-10.json
python baseline.py compare --baseline baselines/jal-2026-10.json --md-out deltas_jal.md
python build_annual.py --html-out annual.html                        # JAL と ANA を切り替えられる月次計画
python track.py actuals --baseline baselines/jal-2026-10.json --truth backlog --out data/jal/actuals_backlog.json
python build_track.py --html-out track.html                          # 追跡（会社ごと・実績 2 通り）
```

使われ方とエンジンの傷み方も運航部門ごとに入れています（`companies.json` の `subfleets`・`wear`）。JAL 本体・JTA・ANA ウイングスごとに年間の飛行回数、1 回あたりの飛行時間、気候を持たせ、区間が短いほど・暑いほど排気温度の余裕が早く減るようにしました（1 回あたりの係数 ≒ (0.65 + 0.2 × 飛行時間) ÷ 1.05 × 気候）。整備直後の最初の 1,000 回で余裕が大きく落ちる 2 段階の劣化、推力の型ごとの整備後の余裕（ANA は -7B24 で 70〜80℃、JAL・JTA は -7B26 と仮定）、寿命部品 3 種（高圧系 20,000・低圧タービン 25,000・ファン 30,000 回）も入れました。エンジンは整備後、同じ会社のどの機体に付くかを機数の比で決めます（会社の中で共有）。

合成データでの主な結果：

### 国内工場の段階的な新設（LEAP-1B、`invest.py`）

737-8 のエンジン（LEAP-1B）の整備を国内に取り込む投資を、20 年のモンテカルロで比べます（前提は `data/leap_invest.json`、確度 A・B・C 付き）。段階 1 は短期入場・部品修理、段階 2 は国内で性能回復まで（試運転設備を共同で）、段階 3 は受託です。「今すぐ全部決める」と「条件付きで段階的に決める」（FY2028 に受領機数と海外の入場待ちを見て判断）も比べます。

```bash
python invest.py --json-out invest.json
python build_report.py --invest invest.json --html-out report.html
```

合成の前提での結果：自社の入場は定常で年 46 件前後と、海外の標準的な工場（年 300〜350 件）より一桁小さく、自社分だけでは海外に出し続けるより得になりません。受託が年 76 件を超えると得になり、補助 25% ごとの効きは約 28 百万ドルと小さい、つまり**規模（受託）が決め手**です。国内の整備費が海外より高いか安いか、メーカーの認可条件、受託の件数、補助率は非公開で、ここが実務で確かめるべき点です。

### 過去の計画との整合と、時間軸のつながり（`history.py`）

2 年前・1 年前にも同じ方法で計画を立てていたとして、同じシミュレーションの歴史を早い時点で切って過去の版を作り直し、その後に実際に起きたことと比べます。

- **当時のリスクの幅に実績が入ったか**：年度ごとの入場件数を、当時の見込みの幅（計画した入場＋想定した率の予定外取卸し、10〜90%）と比べる
- **取卸し時期のずれ**：見込んだ期限と実際の取卸し月の差
- **計画の積み上がり**：前の版の 2 年目が、次の版の 1 年目にどれだけそのまま残ったか

さらに、レポートの「時間軸のつながり」で、ライフサイクル（20 年）→ 設備投資 → 10 年の見通し → 2 年計画 → 年度予算 → 判断期限 → 月次の追跡のそれぞれが次の短い時間軸に落ちているか（つながっていて整合／ずれがある／つながっていない）を示します。合成データでは、国内工場の判断ゲートが今月からの判断期限に載っていないこと、追跡の結果が次の版の前提に返っていないことが、つながっていない所として出ます。

```bash
python history.py jal ana                       # <会社>-history.json
python build_report.py --history-dir . --invest invest.json --html-out report.html
```

### ゲーム理論：交渉と 3 社の分担（`invest.py`）

- **交渉（ナッシュ交渉）**：海外に残る入場の価格は、売り手の原価と、買い手が決裂したときの次善の手の間で決まります。国内に能力を持つと次善の手が良くなり、価格が下がります。段階 1・2 で約 +46 百万ドル。一方、建てた後にメーカーが部品・認可の条件を厳しくする「足元を見られる」分が約 −22 百万ドル。
- **3 社の協力ゲーム（シャープレイ値）**：JAL・ANA・IHI のあらゆる組み合わせで段階 1〜3 を建てた場合の価値を計算。3 社合計は約 −42 百万ドル、各社単独では約 −200 百万ドルなので、全社にとって組むほうが得。取り分は JAL −29、ANA −29、IHI +16（部品修理の技術と設備が価値を生む）。航空会社側は、海外に出し続けるより約 29 百万ドルずつ損なので、補助か受託で埋める必要があります。

- **受託の取り合い（能力を出し合うゲーム）**：日本の 3 社連合・大韓航空・ターキッシュがアジアの受託市場に能力を出すと、同時に決める均衡では各 80 件・利益率 7%。日本が先に決めると 120 件を取れ、段階 1〜3 の価値は −116 → −54 百万ドルに改善（先手の価値）。ただし先に決めることは、段階的に待つ選択を捨てることでもある。受託の件数と利益率は、この均衡から取っています。
- **海外の枠の取り合い（囚人のジレンマ）**：入場待ちが 0.9 か月を超える間（FY2026〜2030）は、JAL・ANA とも割増を払って早めに押さえるのが自分には最善だが、両社とも待つほうが両社とも得。今の 737-800 のエンジンで互いに払い合う割増は今の価値で約 4.6 百万ドル（共同で枠を押さえる価値）。LEAP の入場が本格化する頃には待ちが縮み、取り合いはほぼ起きない。

交渉力・整備会社の利益率・国内で受けられる割合・足元を見られる確率・IHI の効果は、すべて公開値のない仮定（`data/leap_invest.json` に確度 C で記録）です。

### 日々の判断と見方（`usecases.py`）

レポートの上で見方（経営・財務・運航・整備計画・調達・契約・技術・品質）を選ぶと、その人の結論が先頭に出て、関係するカードだけが並びます。日々の判断として次の 6 つを足しました（いずれも「1 基が 1 か月飛ぶごとに積もる整備費」＝平年の整備費 ÷ 取付エンジン、を飛べる寿命の値段として使う）。

| ユースケース | 答え方 |
|---|---|
| 見積もりの承認 | 追加作業は「延びる月数 × 1 か月の値段」まで承認してよい（上限の線） |
| 状態監視の警報 | 今下ろして失う寿命と、待って故障する見込みの損を比べる（要監視のエンジンは残りが短ければ今下ろす、繁忙期にかかるなら常に下ろす） |
| 予備エンジンの数 | 工場側にいる基数をポアソン分布で。今の予備で足りる確率を、工期の長さ別に。持ちすぎの側も：予備 1 基の持つ費用（長期リース相当）と、足りない分の損（短期リース、上限を超えると運休）の合計が最も低い数を、工期ごとに出す |
| エンジンの打診 | 残りの飛行回数に対する上限価格と、ハーフライフの相場（IBA）の比較 |
| 支払いと為替 | 入場時と戻り時の請求で月ごとの支払いと累計、円換算の幅 |
| 信頼性管理 | 予定外取卸し率（1,000 時間あたり）の 3 か月移動平均と警戒値（平均＋3σ） |

## 月次レポート（`build_monthly.py`）

毎月のエンジン定例会議の資料です。月を選ぶとその月末時点の報告になり、前月からの変化も出ます（印刷可）。読む人が知りたい順に、①結論 3 行と会議で決めること、②先月からの変化（前提の確率、新しい外れ、着地見込みの動き）、③実績と計画（今月の入場・戻り、累計）、④今月・来月・再来月に決めること、⑤計画からの外れ（新しいもの先頭）、⑥予備と余力（今後 3 か月、戻り遅れを差し引き）、⑦年度の着地見込み（請求済み・作業中・これから、先月比）、⑧予定外の取卸し。各節に「読み方」を付けています。

```bash
python build_monthly.py --html-out monthly.html     # JAL・ANA、合成実績の 12 か月分
```

### 次の版への引き継ぎ（`roll.py`）

1 年分の実績を次の版の前提に返します。時間軸のつながりで赤だった「追跡の結果を次の版に返す」を埋めるものです。

- **学ぶ**：戻ったエンジンの工期の遅れ、請求 ÷ 見込み、計画外で工場にいる数、故障で前倒しした基数を、観測数で重み付けして前提に混ぜる（重み＝観測数 ÷（観測数＋12）。少ないうちは前の値寄り）。追跡で更新した前提の確率は、次の版の追跡の出発点になる。
- **引き継ぐ**：手配済み（枠の予約・部品の発注）の入場は同じ月・同じ整備範囲に固定。寿命部品キットの手持ちを使用と発注で更新。
- **解く**：同じ機材の歴史を 1 年進めた状態で次の 2 年計画を解く。
- **橋渡し**：前の版の 2 年目 → 機材の状態が動いた分 → 前提を実績で直した分 → 次の版の 1 年目。次の予算要求の説明にそのまま使える形。

```bash
python roll.py jal --actuals data/jal/actuals_backlog.json --out-dir baselines   # data/jal/fleet_next.json・shops_next.json と baselines/jal-roll-2027-10.json
python build_report.py --roll-dir baselines ...
```

合成データでは、JAL は前の版の 2 年目 165 → 次の版の 1 年目 203 百万ドル（機材の状態 +30、前提の修正 +8）、ANA は 110 → 143（+48、−15）。ANA は故障が見込みより少なく、前提を緩めた分が減る側に出ています。

## 階層化したレポート（`build_report.py`）

結論 → ユースケース → 明細 → 前提と出典の 4 段を、グラフで掘り下げる 1 枚のページです。1 段目は会社ごとの 3 行の結論と 24 か月の地図（余力・工場の混み具合・入場の多さ・判断期限を色で）、2 段目は予算の棒・10 年の見通し・打ち手の散布図（費用 × 欠航リスク）・前提の確率の推移・国内工場の損益分岐の地図、3 段目はエンジンごとの横棒、4 段目は出典の有無です。

以下は、これまでのグループ横断の合成サンプル（76 機・5 工場）での説明です。5 工場の比較は、契約更新時の入札のユースケースとして残しています。

### `data/shop_quotes.json` — 工場見積もりとリスク特性

| キー | 意味 |
|---|---|
| `quotes.{WS}.price / tat` | 見積価格（工数・材料・LLP キット込み）と見積 TAT |
| `slots` | 同時受入枠 |
| `transport_cost` / `transport_months` | 往復輸送・保険・スタンド費 / 輸送による追加の off-wing 期間 |
| `overrun_share` | 分解検査で見つかる不具合（findings）による費用超過のうち、自社負担の割合（T&M = 1、固定価格 = 0、上限付き T&M = 0.5 など） |
| `findings.prob / overrun_mean / overrun_cv` | 不具合による費用超過の発生確率・平均超過率・変動係数（対数正規） |

| `volume_commitment.min_visits / shortfall_penalty` | 契約上の最低発注件数（テイク・オア・ペイ）と不足1件あたりの違約金 |
| `max_visits` | 受け入れ上限（中古市場のエンジン在庫など） |

見積もりは「確定値」ではなく **価格 ＋ リスク分布** として入れる点がポイントです。
不具合の有無はエンジン側の性質なので、同じシナリオでは全工場に同じ乱数を使います
（共通乱数法）。工場間の差は「請求される確率」と「誰が払うか」に現れます。

## 解き方

```
1. モンテカルロ   N 個のシナリオを生成（費用超過・遅延・非計画取卸し）
2. SAA           二段階確率 MILP を解く
                 1段目: x[e,k,w,t]（工場・WS・入場月）, S（長期予備台数）
                 2段目: シナリオ×月ごとの短期リース l, AOG a（事後対応）
3. EV 計画       全パラメータを平均値にした確定問題を解く（比較用）
4. 評価          独立な大量シナリオ（既定 5,000）で両計画を評価
                 → 平均、P50/P90、CVaR90、AOG 確率、VSS = EV − SAA
5. ギャップ推定   M 回の独立 SAA の下界平均と、評価値（上界）から最適性ギャップを統計推定
```

2段目は「不足分を短期リース → 別機種での代替運航 → 利益率の低い便からの欠航、の順に安いものから埋める」という閉形式になるため、
評価は MILP を解かずに numpy のベクトル演算で行えます。

リスク回避型にしたい場合は `--cvar-weight λ` を指定すると、目的関数が
`E[総コスト] + λ·CVaR_α[総コスト]` になります（1段目の長期予備費・整備価値も含めた総コストの CVaR）。

## 計画の追跡（`track.py`・`build_track.py`）

年間計画を立てるときに、前提の世界（基準・MRO 混雑・LLP 逼迫・複合ストレス）ごとに最適な **計画案を 4 つ** 一緒に固めておきます（`baseline.py freeze` の `candidates`）。月が進んで実績が入るたびに、次の 3 つに答えます。

1. **いまどの計画に沿っているか**：これまでの入場（ESN × 工場）が各計画案とどれだけ一致するか。計画からの外れ（故障による前倒し、戻り遅れ、費用超過、未入場）の一覧。
2. **前提はどの世界に近いか**：計画時の重みを、実績（戻りの遅れ、故障による前倒し、予定外で工場にいる数、LLP キットの納期回答）が各世界のモンテカルロとどれだけ似ているかで更新した確率。1 か月の証拠で決めつけないよう尤度は弱めています。
3. **今から乗り換えると得か**：入場済みのエンジンはそのまま、未入場のものだけ計画案に従う「乗り換え」の期待コスト差と欠航確率の差（世界の確率で重み付け）。変わるエンジンと判断期限（工場の枠予約、または新たに要る LLP キットの発注）も出し、期限を過ぎた分は緊急手配の割増を差し引きます。

```bash
python track.py actuals --truth backlog --out data/actuals_backlog.json   # 合成実績（混雑の世界で基準計画を実行）
python track.py actuals --truth crunch  --out data/actuals_crunch.json    # 合成実績（LLP 逼迫の世界）
python build_track.py --html-out track.html                               # 月ごとの判定を時点スライダーつきの画面に
```

合成実績での結果：混雑の世界では 6 か月目（外部工場からの戻りが出始める月）に「前提から外れ」を検知しますが、基準計画は混雑に強く、乗り換えても得にならない（→ このまま継続）。LLP 逼迫の世界では最初の月のキット納期回答で検知し、すぐ乗り換えれば約 140 万ドル得、1 か月遅れると新しいキットが緊急手配になり約 50 万ドルに減ります。

## 意思決定レポート（`decide.py`）と分析

要望は同時にすべては満たせないため、優先順位に沿って結論を出すレポートを生成します。

```bash
python levers.py        # よく取られる打ち手を 1 つずつ加えた効果 → levers.json
python explore.py       # 確定できないパラメーター 5 つ × 108 通りで打ち手を最適化に選ばせ、決定木で分類 → explore.json
python sensitivity.py   # 中寿命エンジン価格の損益分岐と、予備の厚さ × 他機種の肩代わりの関係 → sensitivity.json
python decide.py        # 上 3 つを読み込み、前提 4 ケース × 要望 × 代替案 4 つを並列に解いて report.html を出力
```

- **要望の優先順位**（既定、`requirement_priority` で変更可）：欠航確率目標 → 予備バッファ → 契約の最低発注量 → 年度予算 → LLP キットは手持ち → 予備を増やさない。耐空性（期限・要監視エンジン）はその上で、緩めません。全要望が満たせないケースでは、下位から 1 つずつ緩めて成立するところを示します。代替案の推奨は、上位の要望を満たすものを優先（辞書式）し、同順位ならコストで選びます。
- **前提ケース**：基準／MRO 混雑（外部工場 TAT +1 か月）／LLP 逼迫（手持ち半減・調達 12 か月）／複合ストレス。
- **レポートの中身**：結論（推奨・今決めること・承認事項）、あるべき姿（月別の必要装着数＋バッファと使えるエンジン数）、要望の衝突と値段、代替案×ケースの相互評価、判断期限、期限前取卸しの例外理由、打ち手の効果、条件別の答え、見直しのトリガー。

### 分析から分かったこと（合成データ）

- 判断を最も大きく分けるのは **中寿命エンジンの正味価格**：5,500 k$ 以下なら入場の 3 分の 1 以上を中古エンジンとの入れ替えにするのが得、6,500 k$ 以上なら工場整備のみ。市場見積もりの取得が最優先。
- **LLP 逼迫**のときは、下位の要望（予備を増やさない、キットは手持ち）を諦めれば残りは守れる。
- **機材割当**（どの機体をどの便に使うか）は別の最適化問題。エンジン計画との接点で効くのは「他機種が月に何機肩代わりできるか」で、1 機の価値の設定はほぼ計画を変えない。予備が薄い（156 基）と、代替なしの欠航確率 最大 51% が代替ありで 6% に下がる。
- 予備エンジンの追加は、どの条件でも最適化に選ばれなかった（プール契約や代替運航のほうが安く欠航リスクを下げる）。

## 変化点検知（CPD）と前提の更新の整合 — 試作

工場入場は年 10〜30 件しかなく、件数に変化点検知をかけても弱い。代わりに、戻りより先に動く密な系列（工場の見積もり工期・枠の回答リード・LLP キットの納期回答、いずれも週次の合成データ）に BOCPD（Adams & MacKay 2007）と CUSUM をかける（`cpd.py`、`track.py status` の `cpd` ブロック）。

- 合成の混雑世界（JAL 相当）：見積もり工期は 6 週目に +4 週、枠回答は 7 週目に +6 週動き、両検出器とも当該週に検知（月 2）。ベイズの前提更新は 12 か月で 28% までしか寄らず（基準計画が混雑に強く、戻りの遅れが尤度に効かない）、先行指標は 11 か月以上早い。ただし混雑対応計画への乗り換えはどの月でも損なので、早く気づいた価値は 0（気づきの価値ではなく、打ち手側の問題）。
- 合成の逼迫世界：キット納期回答が 6 週目に動き検知（月 2）。ベイズは月 1 で動く（発注時の納期回答が最初から尤度に入る）ので CPD は早くない。ANA 相当では逼迫対応計画への乗り換えが月 1 で +1.0 百万ドル、ベイズが動いた時点の値との差 +0.6 百万ドル。JAL 相当では乗り換えが得になるのは月 8 から。
- 整合レンズ（確かめる層）：月ごとに「変化点が出たか」「前提の確率が動いたか」を並べ、変化点だけ＝4 つの前提のどれにも当てはまらない（世界を追加）、前提だけ＝尤度が強すぎる、と読む。混雑世界は 12 か月「変化点のみ」＝混雑の前提の尤度が弱すぎるか、混雑の定義（TAT +1 か月）が実際の出方と違う。
- 予定外取卸しの率：CUSUM と「3 か月平均＋3σ」を +20% の持続的上振れで比較（300 回）。月 0.5〜1 件の水準では 12 か月以内の検出率は CUSUM 13%・現行 4%、誤警報 5%・4%。どちらも弱く、率の警報は飛行時間あたりの率と EGT 傾向（密な系列）に載せ替えるべき。
- `roll.py` の学習：n/(n+12) の重みは 1 年が同じ体制という前提。混雑の変化点が出たら、それ以前に入場した機の戻りは工期の学習から外し n を戻す。JAL 相当で n 16→11、工期の更新 1.136→1.122 か月、橋渡しの「前提を直した分」+7.6→+7.2 百万ドル（202.9→202.5）。効果は小さいが、変化前の観測を混ぜない方が筋は通る。

未実装：EGT マージンの機体ごとの傾き変化（便ごとの密な系列）による取卸し窓の前倒しとボアスコープの起動。

## PDCA と OODA（二つの輪）— 試作

`ooda.py`：月次会議を待たない暗黙のルール（分解の追加作業＝延びる月数 × v まで当日承認、警報＝寿命が短いか繁忙期なら当日取卸し、戻り遅れ＝短期リース、前提の変化＝ΔV を会議へ、どの前提にも当てはまらない＝安全スイッチで全件を会議へ）。単位価値 v = 年間整備費 ÷ 取付エンジン ÷ 12。ループの時間 T = D + O + A + E とそのてこ。速い輪の結果（ルールの件数と損得、当てはまる世界のない月数、検知の遅れ、安全スイッチの件数）は `roll.py` の学習に入る。乗り換えの推奨には履歴（ΔV が 0.3 百万ドルを 2 か月続けて超える）。橋渡しに「決め方を変えた分」の項（今回は 0）。

## 立て直しが安くなる計画法 — 4 つの側と機能の分類

理論は 2 段階確率計画（リカース付き）。第 1 段（入場時期・整備範囲）を、事後の手当て（リカース）の期待値と裾まで含めて最小にする。

| 側 | 理論 | ここでの機能 |
|---|---|---|
| ① 起きにくくする | 予防保全、先行発注 | 状態監視の警報・傾向、キット先行発注、枠の事前確保 |
| ② 起きても痛くない | ロバスト最適化、CVaR、安全在庫 | 前提ごとの計画案と後悔行列、予備エンジン数、予備費 p80、繁忙期を避ける配置 |
| ③ 起きたら安く立て直す | リカース、リアルオプション、柔軟性 | リース→代替→欠航の充当、ラッシュ入場、緊急キット、グリーンタイム市場、プール契約、乗り換え、暗黙のルール、安全スイッチ |
| ④ 早く気づく | 逐次検知、情報の価値 | 先行指標の変化点、ベイズ更新、ループ時間 T |

`evaluate.py` は費用を「計画どおり」と「立て直し」に分けて返す（`committed` / `recourse` / `recourse_p90` / `recourse_parts`）。打ち手の差分には保険料（`premium`＝先に増える分）と払い戻し（`payout`＝立て直しの減り）。レポート「立て直しの安さ」に、計画案ごとの分離、打ち手の保険料×払い戻し、変化に気づいてからの遅れの費用曲線。

合成データでの発見：基準計画の立て直し費 36.8 M$（JAL、全体の 17%）のうち 33 M$ が所見・為替の超過。予備やプール契約の払い戻しは基準世界ではほぼ 0。立て直しを安くする最大のてこは、予備ではなく契約形態（固定価格・超過の分担率）と所見の見積もり精度である。

### 契約形態を打ち手にする（`actions.py` の `contract_*`、`baseline.py compare`）

上の発見を受けて、各社の契約工場（JAL は GE-TC、ANA は MTU-ZH）の **契約形態そのもの** を打ち手にした。3 つとも `data/companies.json` の `common.contract_forms`（`no_source`、感度分析の対象）で決まり、工場が引き受けるリスクの分だけ見積もりに上乗せする。

| 打ち手 | 自社の超過負担 | 見積もり | 備考 |
|---|---|---|---|
| `contract_fixed` 固定価格契約 | 0 | +8% | 整備範囲ごとの固定価格 |
| `contract_share50` 超過の折半 | 50% | +3% | 所見の費用を工場と分担 |
| `contract_pbh` 時間課金（PBH 型） | 0 | 所見込みの期待費用（price×(1+prob×overrun_mean×share)）で固定、さらに +5% | 飛行時間あたりの課金を 1 件あたりの固定価格で近似。工期の遅れ分布は変えない |

合成データでの結果（基準からの増減、k$、期待値。保険料＝先に増える分、払い戻し＝立て直し費の減り、p90＝立て直し費の 90 パーセンタイルの差）：

| 会社 | 打ち手 | 総コスト | 保険料 | 払い戻し | 立て直し p90 |
|---|---|---|---|---|---|
| JAL（基準 218,684、立て直し 36,829 うち超過 33,222） | 固定価格 | −3,277 | +26,798 | +30,075 | −32,810 |
| | 折半 | −4,621 | +9,903 | +14,524 | −16,672 |
| | PBH 型 | +18,651 | +48,701 | +30,051 | −29,994 |
| ANA（基準 151,462、立て直し 30,207 うち超過 25,659） | 固定価格 | −2,444 | +20,872 | +23,316 | −24,078 |
| | 折半 | −3,500 | +7,827 | +11,327 | −12,701 |
| | PBH 型 | +14,523 | +37,700 | +23,177 | −21,762 |

読み方：所見の期待超過は価格の約 9%（0.45 × 0.2）なので、+8% の固定価格は期待値でもわずかに得で、立て直しの裾（p90）を 3 割以上削る。折半は保険料が小さく期待値では最も得だが、裾は半分しか削れない。PBH 型は所見込みの期待費用に +5% を重ねるため、この前提では期待値で損（裾の削減は固定価格と同じ）。いずれも欠航確率は変わらない。工場側の上乗せ率は根拠のない仮置きなので、実際の見積もりに置き換えて感度を見る。

## 工場の容量が契約量にどう反応するか — 3 つのシナリオ（試作）

`shop_response.py`：「何基を長期契約に出すと、何年後に枠がいくつ増え、単価がどう動くか」を、契約工場の反応の型 3 つで年 0〜6 について出す。前提と出典は `data/shop_response.json`（公開情報は桁の根拠のみ：1 工場の増設は +30〜150 件/年で 2〜4 年先（SAESM モロッコ 70→100 件/年、MTU 珠海 +50%→450 件/年）、GE は流れ生産で TAT を年 10% 超改善、世界の CFM56 入場は 2028 年まで年 2,300〜2,400 件で横ばい、枠は契約量に概ね比例して配分）。航空会社の年間入場は基準（`baselines/*-2026-10.json` の `norms.visits_per_year`）から JAL 約 20 件、ANA 約 10 件。同時枠 = 件数 × TAT ÷ 12。

    python3 shop_response.py jal --commit 20 --out shop_response/jal.json
    python3 shop_response.py ana --commit 10

- A「反応なし」：枠も TAT も単価も動かない。
- B「契約量に応じて増強」：コミット V ≥ 15 件/年なら工場が 3 年後に +30 件/年を増設し、航空会社の取り分は V ÷ 工場全体 300 件/年 × 30。単価は長期契約で −3%。
- C「混雑を価格に転嫁」：枠は据え置き、工場稼働率 > 0.9 の間は単価 +5%/年、TAT は −10%/年（下限は今の 60%）。TAT が縮む分だけ実効の枠（年に通せる件数）が増える。

| | JAL（GE-TC、10 枠、TAT 3.4 か月） | ANA（MTU-ZH、7 枠、TAT 3.7 か月） |
|---|---|---|
| B の発動 | V=20 で発動。3 年目に +2.0 件/年 = +0.57 同時枠、単価 0.97 | V=10 では発動しない（あと +5 件/年）。V=15 なら 3 年目に +1.5 件/年 = +0.46 枠 |
| コミット 10／15／20／25 | 発動なし／3 年目 +1.5／+2.0／+2.5 件/年（+0.43／0.57／0.71 枠） | 発動なし／3 年目 +1.5／+2.0／+2.5 件/年（+0.46／0.62／0.77 枠） |
| C | 単価は 1 年目に 1.05 で頭打ち（TAT 短縮で稼働率が 0.9 を割る）。TAT 3.4→2.0 か月で 10 枠が年 35→59 件分に | 同じく 1.05 で頭打ち。TAT 3.7→2.2 か月で 7 枠が年 23→38 件分に |

読み方：長期契約で「買える」枠は 3 年後に +0.4〜0.8 同時枠と小さく、需要が横ばいなら混雑は増設より TAT 短縮で先に解ける。単価は B で −3%、C で +5% の幅。

注意：発動しきい値 15 件/年、増設 +30、工場全体 300 件/年、工場稼働率 0.95、−3%／+5% の価格、TAT 下限 60% はすべて出典なしの仮定（`no_source`）。また 1 社の混雑（自社の枠待ち・戻り遅れ）は工場からは見えず、工場を動かすのは契約量だけである。自社の困り具合を入力にしても枠は増えない。

## お金の仕組み — 前払い・税の期ズレ・規模の仕組み

`finance.py` は、計画を変えずに同じ計画の「お金」を動かす仕組みを、凍結した基準計画の上で簡単な式で値付けする（`data/finance.json` に前提と出典）。前払い割引、損金の期ズレ（時間課金型は飛行のたびに損金、都度払いは入場時。繰延であって節税ではない）、消費税・関税（海外修理は課税対象外、再輸入減税）、補助金の圧縮記帳、予備のセール＆リースバック、そして大手だけが使える仕組み（アライアンス共同の予備プール＝必要予備は √n/n、OEM の大口ティア、グループ整備会社への内製、リース機の整備積立金を信用状で代替、複数年契約の値上げ上限、為替の自然ヘッジ）。税・会計の項目は「要確認」の印を付け、合計から外している。

同じ仕組みは `fin_*` の打ち手としてシミュレーションの中にもある（`python baseline.py compare`、⑥ お金の仕組み）。式とシミュレーションで違いが出る項目が要点：為替固定は期待値を変えないが悪い 1 割を大きく縮める、共同予備プールは予備が制約でしか効かないのでシミュレーションでは 0、大口ティアは安くなった分だけ計画が再最適化されて式の 2 倍になる。

## 税引後で比べる — 同じ計画を税引後の物差しで

`tax.py` は計画を変えずに、同じ計画の費用を税引後の物差しに直す（`data/tax_params.json` に前提・出典・確度 A/B/C／`no_source`）。税のために工場や時期を選ぶ話ではなく、税引前で並べた順位が税引後にどう見えるかを確かめる道具である。

1. **年度ごとの区分と盾**：入場ごとの費用を修繕費（当期の損金）と資本的支出（航空機 10 年・定率法で償却）に分け、年度ごとの税の盾（損金 × 実効税率）、税引後の費用、盾の現在価値、繰延税金負債の概算を出す。区分は合成の仮定（PR 100% 修繕、CORE 60/40、FULL 45/55）で、実際の会社の会計方針ではない。
2. **年度をまたぐ動き**：「外部工場の TAT が 1 か月延びたら」で費用が年度間を移る分の税引後の差と、納税が遅れる時間価値（税率 × 移る額 × (1 − 1/(1+r))）。
3. **予備エンジン**：購入（5,500 k$、償却の盾、残存簿価）／長期リース／短期リースの税引後の現在価値を 2 年と 10 年で。
4. **国内工場**：invest.py の方針ごとの税引後 NPV（償却の盾つき）と、補助金を受取時に課税する場合と圧縮記帳（法人税法 42 条）の 2 行。
5. **工場ごとの実効費用**：FULL 1 件あたり、見積もり＋輸送＋控除不能な関税・消費税（修繕のための輸出・再輸入の減税、民間航空機協定で航空機部品は無税、輸入消費税は仕入税額控除で中立＝0）＋遅れの費用（翼を離れる期間の差 × 短期リース 130 k$/月）− 税の盾の現在価値。
6. **前提と出典・見張る指標**：実効税率（東京都・大法人 30.62%、確度 B）、防衛特別法人税（法人税額の 4%、2026 年 4 月以後開始の事業年度、確度 C）、耐用年数省令、関税定率法 11 条、圧縮記帳、税効果会計（C）。OODA で見張るのは税率改正・防衛特別法人税の開始・耐用年数の改正・修繕費区分の判断・補助金の採択。

合成データ（JAL）：税引後の整備費は 2 年で 290 百万ドル（税引前 373、盾の現在価値 101）。予備 1 基は 2 年なら長期リース、10 年なら購入。工場の税引後の順位は税引前と同じ（IND-ASIA → IND-NA → IND-EU → OEM-ASIA）。

## 退役までの入場列 — エンジン計画の芯（`runout.py`）

2 年の窓は、機材が退役するまでの長い問いの一部でしかない。`runout.py` はエンジン 1 基ごとに「今日から退役まで、あと何回工場に入り、その入場は何を回復すれば退役にちょうど届くか」を並べる。

- 窓の中は凍結した計画の入場（そのまま）。窓の後は、20 年シミュレーション（最初の 5 年は捨てる）が残した全エンジンの状態（`fleet.json` の `engine_state`：EGT 余裕・寿命部品・機ごとの劣化係数）から、平均の劣化物理で退役まで決定論的に飛ばし、限界が来たら**退役まで持つ最軽の整備範囲**（run-out）を選ぶ。
- 退役は移行計画（`transition`：受領 1 機ごとに 1 機退役、no_source）で位置が減る。どの機を先に退役させるかは方針：**次に入場が近い機から**（採用）／寿命部品の少ない機から／無作為。
- 退役時に残る寿命（部品サイクル・翼上月数）をハーフライフ換算（`mx4_params`）で値付けし、「寿命を残して退役する機」「退役直前の重整備」を印にする。
- レポート「退役までの入場列」：毎年の入場と退役、機ごとの列（窓の帯・入場の棒・退役の菱形・限界が計画より早い赤い印）、方針の比較、印の付いた機。
- 合成データ（JAL）：2036-03 の最終退役まで 123 基で入場 56 件（窓の後 16）、生涯費用 487 百万ドル、退役で処分する残存価値 97 百万ドル。無作為の退役順だと入場 612 件。空の年は退役（年 13 基）が限界の近い機を吸収した年で、注釈に出る。

## PDCA／OODA の観点で見直す AI 機能（`review.py`）

計画の数値（凍結した計画・追跡・変化点・暗黙のルールの再生・次の版への橋渡し・退役までの入場列）を、二つの輪のどの段が弱いかという**見直し**に変える。

- **規則層**：事実パック → 症状表（輪・段・重さ・指摘・根拠・会議で聞くこと）。毎回同じ判定で、テストが押さえる（`tests/test_review.py`）。例：制約を緩めた計画（Plan）、計画との一致率（Do）、いちばん確からしい世界（Check）、Δ決め方 = 0（Act）、先行指標が前提より早い（Observe）、変化点と前提の整合（Orient）、承認線 v の純額（Decide）、D + A ≤ R（Act）。
- **AI 層**：Claude（公式 Anthropic SDK、既定 `claude-opus-5`、adaptive thinking、ストリーミング）が事実パックと症状表から、総評・PDCA 4 段・OODA 4 段・会議で聞く 5 つの問い・次の版で直す 3 点を書く。資格情報（`ANTHROPIC_API_KEY`）がなければ規則層だけを返し、その旨をレポートに出す（`REVIEW_NO_AI=1 ./run_all.sh` で明示的に省ける）。
- レポート「PDCA／OODA の見直し（AI）」：段ごとの最悪度の格子、見直しの本文、症状表。

## 客席の需要 — 一つ上の層（`demand.py`）

エンジン計画の上には機材の移行があり、その上に路線と客席の需要がある。上の層が下の層の「必要」を決め、下の層は上の層に「余力」と「限界」を返す。`demand.py` はその一番上の段を、下への線（必要機数の出所）と上への返し（余力の客席換算）の 2 本だけで結ぶ。

- **市場**：国交省 航空輸送統計速報（e-Stat）の国内定期 旅客の月次（旅客数・座席キロ・人キロ・利用率）と年度系列（2018〜2025 年度）。需要の季節指数を、エンジン計画が仮定する運航指数（`lifecycle.FLIGHT_INDEX`）と重ねて、ずれの大きい月を出す。
- **各社**：ANA は公式の月次輸送実績 PDF、JAL は公式 PDF が取得できず報道の転載値。市場に占める割合と、利用率が閾値（85%、仮定）を超えた月の「満たせなかった需要」の下限。
- **エンジンとの接続**：退役までの列の運航側（余力）÷ 2 = 飛ばせる機数 → 月の便数 × 座席 × 区間距離 = 上乗せできる座席キロ。足りない月は失う売上（利用率 × 単価、仮定）。需要が逼迫し、かつ余力がある月が「伸ばせる月」。
- 実データ（市場）：FY2025 の需要は FY2019 比 +13%、供給は −1%、利用率 70.9% → 81.3%。JAL の国内線は 2026 年 2〜3 月が利用率 87〜90% で逼迫、満たせなかった需要の下限は取れた月だけで 3.3 億人キロ（≈ 43 万人）。窓の中のエンジン余力は 737-800 供給の 15%。
- 仮定（要差し替え）：737-800 が国内線 ASK に占める割合、利用率の閾値、単価。`data/demand.json` に出典と確度。

### 過去の需要から計画の前提に直す（`plan_from_demand.py`）

需要の層から、季節の形（市場の月次 RPK ÷ 平均）、需要の伸び（市場 RPK の年率）、稼働（利用率を閾値に戻しつつ伸びを運ぶのに要る供給の比、上限 +10%）を導き、今日のエンジン状態から先の前提だけを変えて窓を引き直す。過去は書き換えない。今の前提との差（期限が来る機、窓の動き、必要エンジン数、平年値）と、再計算した計画（費用・入場・欠航リスク）を並べる。稼働が上がれば寿命部品と EGT の限界が早まり、伸びれば必要な位置が増えて欠航リスクが上がる。

### 需要から何機・何基要るか（`fleet_from_demand.py`）

`plan_from_demand.py` と `demand.py` の上に足す層。会社の 737 分の需要（市場 RPK × 会社シェア × 737 シェア × 季節指数 × 伸び）を月ごとに p10／p50／p90 の帯で引き、**要る機数** ＝ 需要 ÷ 目標搭乗率 ÷ 1 機が 1 か月に出せる座席キロ ＋ 機体整備で止まる機、**要るエンジン** ＝ 飛ぶ機 × 2 ＋ 予備（見張りが求めた短期リース分を含む）を出す。判定は p90（足りない月）、費用は p50。足りない月の打ち手（稼働を上げる・ウェットリース・退役を遅らせる・見送る）を費用とエンジン側への影響つきで並べ、余る月は遊ぶ機の維持費を出す。年度の始まりに固める数字（年度ごとの最大必要機数、整備費と伸びによる増分、逼迫月の搭乗率・エンジン余力・増便の損得）を `planning_season` に、20 年の退役後の機数と需要の差を `long_view` にまとめる。737 シェア（no_source）が機材と整合するかも確かめ、合わなければ整合するシェアを返す。

```bash
python3 fleet_from_demand.py jal --out fleet/jal.json     # ana も同じ。--runout/--shortage/--growth は既定で各ディレクトリを見る
```

### 空港と航空会社をつなぐ — 羽田の枠と、複数機種の機材割当（`airport_slots.py`・`route_fleet.py`）

二つの層を重ねる。

**空港側の層**（`airport_slots.py`、`data/hnd_slots.json`）。羽田の国内線の発着枠は 1 日 465 枠（1 枠＝1 往復、1 時間に最大 90 回）で、会社ごとに配分される。地方路線にしか使えない枠があり、便数の少ない路線の枠は転用が制限され、使わない枠は回収の対象になる。配分は 5 年ごとに見直され、前回（2019）は 19 枠回収・16 枠再配分、次は 2028 年。この層は会社ごとに、幹線 4 路線（羽田–新千歳・伊丹・福岡・那覇）に使っている往復便数の合計（枠）、路線ごとの便数の幅、枠を使う下限（98%）を出す。同じ路線の他社の便数（合計だけ持つ）と自社の便数から、路線の旅客の取り分（便数の比率、S 字の指数 α）を出す。出典は国交省の資料（ファイルに URL）。

**航空会社の層**（`route_fleet.py`、`data/routes_trunk.json`）。路線全体の旅客（2024 年の公開値、全社・両方向）を 2026-10 まで伸ばし、自社の取り分を掛けて、自社の月ごとの需要にする。1 日の飛び方（羽田を出て羽田に戻るパターン）を単位に、機種 × パターンの機数を月ごとに整数計画で解く（機材割当モデル、Hane ほか 1995）。目的は運航費 ＋ 737 のウェットリース ＋ 失う売上の最小化。縛りは、機種ごとに幹線に回せる機数（国内線の機数から他の路線・整備の分を引いた上限、根拠はファイルに）と、空港側の層の枠と便数の幅。便数が変われば取り分も変わるので、取り分と便数が落ち着くまで解き直す（年次の版は許容差なしで解き、便数を一つに定める）。便数の下限と枠を使う下限は、機体がなければ欠航できる緩い縛りにし、欠航には罰金を置く。

**1 便ごとの取りこぼし**。1 便が運べるのは、その便の需要と座席の小さいほう。便の需要は路線の平均のまわりにばらつくので、満席の便があっても月平均の搭乗率は 100% にならない。1 日の飛び方の各便を出発時刻で朝夕のピーク（7〜10 時・16〜20 時）と昼の谷に分け、ピークの便の平均需要を谷の 1.3 倍とする。同じ時間帯の中のばらつき・曜日・予約の取りこぼしは、対数正規分布の変動係数（合わせて 0.24）で表す。機種ごとに「1 便で運べる人数の期待値」を出し、整数計画の中では線形の係数として使う。昼の谷に大きい機体を入れると空席が増えるので、便数が枠で決まっている路線では 767 のような中間の大きさの機材も選ばれる。

**運賃と運航費**。1 人あたりの運賃は距離の 0.5 乗に比例させ（短い区間ほど 1 キロあたりが高い）、路線の旅客で重みをつけた平均の単価は会社の単価に合わせる。1 時間あたりの運航費は 737 を 3.5 k$ とし、ほかの機種は座席数の 0.7 乗で決め、古い機種（767・777）は 1 割増し。どちらも仮定で、2024 年の路線別の座席利用率に合う組み合わせを試して選んだ。p10／p50／p90 で解き、借りるかどうかも解の中で決まる（借りても枠がなければ飛べない）。

**2028 年の再配分シナリオ**。幹線の枠を ±3・±5・−9 往復（配分の 5% が約 9 枠）動かし、便数・取り分・旅客・売上・運航費・737 の飛行回数とエンジンの入場の前倒しを、対象年度で比べる（`fleet/<company>.json` の `trunk.slot_scenarios`）。変化はすべて幹線に寄せ、他社の便数は据え置く。

737 は幹線と地方路線で全機を分け合う。年次の版で 737 が幹線で運ぶ人キロの割合が決まり、会社の 737 の需要の残りが地方路線になる。エンジンは機種ごとに、幹線のパターンの飛行回数と機種全体のふだんの回数を混ぜた稼働倍率を `plan_from_demand.build_fleet(..., fleet_key)` に渡し、入場時期の動きと平年の整備費を出す（737・767・787。他の機種はエンジン計画のデータがないので回数だけ）。エンジンの交換は羽田の格納庫で行い予備も羽田に置くが、エンジンの工場整備は別の場所（成田）にある。

ブラウザのデモには、解を前もって出したファイルを渡す（ページの中では解かない）：

```bash
python3 export_trunk_assignment.py jal --label "Company A" --out trunk_assignment.json   # 月 × 分位の機種別の割当・枠・搭乗率・乗れない旅客・費用、約 30 KB
```

### 羽田の容量のキャップと、その先（`capacity_scenarios.py`、`data/destination_airports.json`）

羽田の幹線の便数が増えないまま需要が伸びると何が起きるか、キャップが外れたら何が起きるかを、同じ機材割当を 1 年度ずつ解き直して比べる（p50）。

- **年ごと**：需要だけを年の伸び率で伸ばし（FY+0〜+5）、羽田の便数は据え置き。乗れない旅客・失う売上・差し引き、機種ごとのエンジン（稼働倍率・前倒しの基数・整備費）を、便数を需要に合わせて増やした場合（キャップが外れた仮定）と並べる。
- **大型機中心**：幹線の A350 を 15・17 機に増やす（足す機体に 1 機・月 1,100 k$ の所有またはリースの費用、no_source）、737 を幹線から外す。売上・運航費・足した機体の費用を引いた差し引き、エンジン。
- **対向空港**：羽田の幹線の枠を +10〜+45 往復にしたとき、向こう側の空港（新千歳 1 時間 50 回、伊丹 1 日 370 回のうちジェット 200 回、福岡 第 2 滑走路で 1 時間 45 回、那覇 第 2 滑走路で年 24 万回）が受けられるか。空港ごとの自社の余地（今の便数に上乗せできる往復、no_source）を路線ごとの上限に重ね、受けられない枠・先に詰まる空港を出す。

エンジンの窓は、幹線の機材割当が実際に飛ばすサイクルで出す（計画の上限 ×1.10 で切らない）。

あわせて感度を出す：需要の伸び ±1 ポイント（5 年後）、為替 140・170 円/$（最初の年）。

```bash
python3 capacity_scenarios.py jal --out fleet/capacity_jal.json   # 約 40 秒
```

### 運賃をどこまで上げるか（`fare_scenarios.py`）

羽田のキャップの下で便を増やせないとき、もう一つの手は運賃。月ごとの機材割当（`route_fleet.price`）が、路線ごとの運賃を今の 0.8〜1.5 倍（0.05 刻み）から選び、売上 − 運航費 − リース費 が最大になるようにする。運賃を上げると旅客が減り、同じ枠を小さい機体で飛べるので運航費が下がり、乗れない旅客も減る。需要は今の運賃を通る直線（そこでの弾力性 e）。値は文献を原典で確かめた `data/elasticity/literature.json` から：市場全体が一緒に動くと約 −0.8、他社が据え置くと路線で約 −1.4。弾力性一定の曲線は、需要が非弾力的だと運賃を際限なく上げてしまうので使わない。弾力性 −0.8・−1.1・−1.4 と年度（FY+0・+3）で、今の運賃と比べる。羽田の枠 +20 往復と運賃の組み合わせも、対向空港の上限なし・ありの両方で出す。

```bash
python3 fare_scenarios.py jal --out fleet/fares_jal.json   # 約 4 分
```

**弾力性の根拠（`fare_elasticity.py`、`data/elasticity/`）**。文献値（InterVISTAS 2007、日本の OD 需要関数・ネスティッド・ロジットなど）を原典で確かめ、出典と注意を `literature.json` に置いた。あわせて公開データで推定する：国交省の航空輸送統計年報（路線 × 月の旅客・座席、10 路線、2006〜2019 年）を、消費者物価指数の航空運賃（総合で割った実質）・景気動向指数・路線の季節と傾向で回帰し、原油の円建て価格（遅れ 1・3・6 か月）を操作変数にした 2SLS も出す。運賃の指数が全国一本なので、出るのは市場全体の弾力性で、絶対値の下限としてしか読めない（需要が強いと運賃が上がる、枠で詰まった路線は運賃が下がっても旅客が増えない）。

```bash
python3 fare_elasticity.py --out fleet/fare_elasticity.json
```

### 地上の交通で容量を動かす（`corridor_scenarios.py`、`data/corridor.json`）

三つの場合。(1) リニアが新大阪まで来て羽田–伊丹の旅客が鉄道に移る（航空に残る割合は国交省の予測 0.66・0.46・0.22）：会社 A と他社が空いた枠を他の幹線に移すか否かの 4 通りを、機材割当で解く（`route_fleet.build(corridor=...)`：路線の市場の倍率・便数の幅・枠を使う下限・他社の便数の移動）。(2) 鉄道でつないだ空港（成田・中部・山梨）：アクセスの時間差 × 時間価値 ＋ 運賃差を運賃と同じ需要曲線に当て、羽田で乗れなかった旅客のうち飛ぶ割合を出す（ふるい分け）。(3) 伊丹を縮める：跡地の値と旅客の追加の費用を、不確かな入力を振って確率で比べる。

リニアの 4 通りは会社 A・B の両方を解き（`linear_game`：ナッシュ均衡、二社の合計が最大の組み合わせ、均衡より両社とも得なセル）、会社 B の運航費の係数を 5 通りに変えて結論が残るかを確かめる（`game_robustness`）。運航費の係数は `calibrate_costs.py`（2024 年の需要で解いた路線ごとの搭乗率を 2024 年の座席利用率に合わせる格子探索）で選ぶ。

```bash
python3 corridor_scenarios.py jal --out fleet/corridor_jal.json
```
python3 calibrate_costs.py ana          # 係数の格子と、路線ごとの搭乗率のずれ（--write で routes_trunk.json に書く）

### 文書の批判役（`doc_critic.py`、`.claude/agents/doc-critic.md`）

モデルが出すのは数字、文書が出すのは主張。批判役は、主張が根拠を超えているところを指摘する。`review.py` と同じ二層。

- **規則層**（毎回同じ判定）：言い過ぎの語（決まっていた・必ず・明らか・証明・すべて など）、出力（`fleet/*.json`・`data/**/*.json`）に見つからない小数（表示の桁で照合、10 の累乗の単位のずれは許す）、出典も no_source の印もない仮定、文書自身が「未確認」とした箇所、公開リポジトリに置かない語（実在の会社名・メタ）、限界の節・合成データの断り・表の列数。
- **AI 層**：Claude が本文と指摘表を読み、五つの読み手（査読者・経営者・整備計画の担当者・反対論者・初めての読者）から、言い過ぎと直し案、根拠の弱い数字、抜けている別の説明、直す順番を書く。資格情報がなければ規則層だけ。同じ指示を Claude Code のサブエージェント（`.claude/agents/doc-critic.md`）にも置いたので、API キーなしでもセッションの中で回せる。

```bash
python3 doc_critic.py handover/04_docs/fleet_from_demand_結果.md --out review/doc_critic.json --md review/doc_critic.md   # 非公開の下書きは --private
```

## 過去で検証（`backtest.py`）

同じ方法を過去の各時点で回し、その後に起きたことと比べる。エンジン計画は 20 年シミュレーションを履歴として過去 8 版で（期限の予測誤差、年度ごとの較正、件数と費用、計画外取卸し、版の安定性）、需要の伸びは実データの年度系列で（直近・長期・混ぜ方の規則をその年度までのデータだけで当てる）。判定は `review.py` の「確かめる」に流れ、レポート「過去で検証」に図と表で出る。

## 型式の時計（`typelife.py`）

エンジン 1 基の時計（サイクル・EGT）の上に、型式の世代の時計（就航 → 生産終了 → 退役の波 → 次世代、間隔 約 20 年）がある。`data/engine_types.json` に CFM56-7B と LEAP-1B の年表（出典つき）と仮定（残存価値の低下曲線、晩年の部品値上がりと工期、次世代の年齢別の受領遅れ確率）。退役までの列の残存価値を退役年の型式年齢で割り引き、当社の最終退役と世界の退役の波の位置を示す。

## 打ち手の順番（`playbook.py`）

診断（遅いのはキットの納期と判断のリード、費用を膨らませるのは所見）から決めた順番「キット → 契約 → 第二工場の選択権」を、同じシミュレーションに順に重ねて基準・逼迫・晩年（`late@<枠の減り>`）の 3 世界で解き、期待値・欠航リスク・立て直し費・ループの時間と、誰が・いつ・期限・引き金を出す。第二工場は新設でなく枠組み契約の選択権（`second_shop`）。
