# 要望一覧（依頼者から繰り返し確認されるもの）

このサンプル群への依頼者の要望を、作業のたびに見返せるよう記録します。
状態：✅ 合成データで動く見本がある ／ 🟡 一部だけ ／ ⬜ 未着手。新しい要望は末尾に追記し、対応したら状態を更新してください。

> **✅ は「実務で使える」ではありません。** ここにあるのは、公開情報から推定した合成データの上で、判断の骨組み（何を比べ、どう結論を出すか）を示した見本です。実務で使うには、下の「実務との距離」にある項目がすべて要ります。この分野では整備管理システム、メーカーの状態監視、計画ツールに毎年大きな開発費が投じられており、それらを置き換えるものではなく、その上で判断を速くする層として位置づけます。

## 実務との距離（見本から実務へ）

| 領域 | 実務で要るもの | いまの見本 |
|---|---|---|
| データ | 整備記録システム（部品の出自、寿命部品、取卸し・入場履歴）、メーカーの状態監視データ、工場の見積もり・所見・請求、契約、会計との接続。記録の欠けや食い違いの扱い | 合成データのみ。接続なし |
| 技術の規則 | 耐空性改善通報・技術通報、整備範囲の計画指針、寿命部品の型ごとの制限、構成・推力の型、整備マニュアルの限度 | 整備範囲 3 種、寿命部品 2 束に単純化 |
| 判断の範囲 | 決めることの一覧 36 件（見積もり承認、トレンド警報での取卸し、ボアスコープ所見、保険・保証、返却条件など） | 計画・予算・追跡の約 9 件 |
| 数字の確からしさ | 自社実績での較正、専門家による検証、過去の判断との突き合わせ（後ろ向き検証） | 公開情報からの推定。検証なし |
| 業務と責任 | 承認の流れ、監査の記録、当局に承認された整備規程・信頼性管理との整合、誰が責任を持つか | 判断ルームの承認ボタンのみ |
| 運用 | 権限管理、稼働監視、データの版管理、変更管理、利用者の教育 | なし |

## SDK の改善点（例を作る中で見つかったもの）

| # | 改善点 | 影響 |
|---|---|---|
| S1 | SDK の入口が常に xterm を読み込むため、Node のスクリプトからそのまま使えない。Node 用の入口が必要 | サーバー側・定期実行からの利用 |
| S2 | セッションの出力やファイルを REST で読めない。追加の指示（フォローアップ）も送れない | 結果の取り込み、会話の継続 |
| S3 | `addPane` に `prompt` がなく、2 つ目のペイン（検証担当など）に指示を渡せない | 複数エージェントの役割分担 |
| S4 | `WorkAGI` に `KnowledgeClient` を作る入口がない | 一貫した使い勝手 |
| S5 | セッションや文書にメタデータを付けられない（ラベルと ID で区別するしかない） | 版管理、基準との対応付け |
| S6 | 同期コネクタの設定キー、`schedule` の時間帯、`prompt` の渡され方、既存 ID でのアップロードの上書き挙動が文書化されていない | 実運用の前提 |
